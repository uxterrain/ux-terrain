Point of view · Design systems

The ground layer

A design system used to be a kit you flipped through. That worked when a person drew every screen and read every note. It fails the moment the interface is assembled later — by a second team, a pipeline, or an agent that has never opened the file. We stop shipping a kit. We ship the ground the product stands on.

Tokens are bedrock. Primitives are paths. Patterns are weather — they change, but they never leave the ground.

The cut this whole page is drawn from

Most teams meet that pressure by decorating faster. A copilot in the file. A prettier kit. A longer wiki. The product still drifts, because the decisions never left the guidance page. Spacing is a habit. Color is a screenshot. A card is “whatever we did last time.”

The work is to move those decisions into something both a designer and a machine can be held to. Named tokens. Primitives with states and an accessibility contract. A trail that runs both ways between the design file and production, so neither can lie to the other. When a composition is wrong, it fails a check — it does not wait for a review meeting that may never happen.

Three holds

Not new tools. A change in what the system is allowed to forget.

The decision

Wiki → tokens

If a value isn’t named, it isn’t a decision — it’s sediment. Color, type, space, and motion live in variables both files can share, not in a paragraph someone has to remember.

The trail

Handoff → two-way sync

Static redlines are a one-way walk that immediately grows over. We wire Figma and code through MCP so the canvas and the repository stay on the same map.

The edge

Meeting → a check that fails

Review doesn’t scale to runtime-assembled UI. A primitive that is the wrong choice, or a contrast that slips, should fail before a user ever sees it.

A cut through the system

Most libraries are arranged like a catalog: pages of components, a few tokens at the back. We read them the other way — from the ground up. Products are weather. They should never have to invent bedrock.

What a core actually looks like

Pull a sample from a live admin surface and you can tell, immediately, whether the ground is named. One core is sediment: leftover hex, a spacing habit, a blue that means three different things. The other is logged. Same product. Different honesty.

The trail that must run both ways

A handoff is a path that washes out overnight. The useful picture is a trail with cairns: Figma on one side, production on the other, tokens stacked in the middle so neither walker gets lost. MCP is how we keep the cairns from being kicked over.

How we lay the ground

We don’t boil a library. We survey one surface, name what it already stands on, and only then cut paths. The point is a trail the next team can walk without us.

Stake 01

Survey the drift

Find where the file already lies to the code. Pick one surface, not the whole kit.

  • Diff Figma variables against what ships.
  • Mark unnamed sediment: hex, magic space, one-off type.
  • Choose the surface closest to being assembled later.

Stake 02

Name the bedrock

Only the tokens that surface actually stands on. A short dictionary beats a theme file nobody uses.

  • Color, type, space, radius — named for meaning, not for a page.
  • Publish the same names into CSS custom properties and Tailwind.
  • Prove a renamed token moves in both files the same afternoon.

Stake 03

Cut the paths

Primitives with states, contents, and an accessibility contract. Agents and humans pick from this set. They do not invent a new one.

  • Ten primitives, fully stated — not a hundred half-drawn.
  • Wrong composition fails a check in review, then in CI.
  • The second component costs a fraction of the first.

Stake 04

Let the weather in

Patterns and product UI can change. The ground does not. Keep the trail open so drift has nowhere to settle.

  • MCP both ways, so the canvas cannot silently fork.
  • A dashboard leadership already watches: drift, checks, time-to-sync.
  • Hand the transect to the team. We leave a map, not a dependency.
